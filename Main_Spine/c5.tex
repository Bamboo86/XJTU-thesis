\xchapter{平面几何问题求解系统}{Plane geometry problem solving system}

为进一步验证前述研究成果在实际应用场景中的可行性，并推动相关方法由离线实验向系统应用转化，本章在前述工作的基础上开发了平面几何问题求解系统，对多模态输入、求解模型调用与结果可视化流程进行集成。本章围绕系统需求分析、设计与实现、展示与测试等内容展开说明，重点介绍几何求解模块的工程化实现过程。

\xsubsection{功能性需求分析}{Functional Requirement Analysis}

平面几何问题求解系统主要定位为面向教育场景和几何智能推理研究的辅助平台，适用对象包括进行几何学习的学生、准备教学资源的教师以及相关领域的算法研究人员。与仅输出最终答案的传统数学工具相比，本系统更强调题目输入、模型调用、推理过程展示与结果对比之间的协同。在功能设计上，系统主要包含以下几项核心需求：

在题目生成与输入方面，系统应具备几何问题生成及问题拓展衍生功能，能够根据设定的难度、几何基元及定理参数生成相应题目。需要说明的是，题目生成属于系统的辅助功能，本章重点关注几何问题求解流程及其工程实现，因此此处仅对其功能需求进行概括性说明。针对用户自定义求解，系统需支持输入平面几何题目的文字描述并上传几何图像，以贴近“题干+配图”的多模态组织形式。

在多模态求解与模型调用方面，系统应在统一框架下集成四种求解算法：树状搜索、演绎可解释、大模型以及神经符号求解。前端需提供模型选择与切换功能，后端则负责不同模型运行环境的管理与调度，实现同一题目在不同求解方法下的横向对比。

在求解流程与可视化展示方面，系统应支持多模型任务的统一提交与结果展示。提交任务后，系统根据各模型执行状态返回对应结果，并在前端页面中进行分区域展示。系统不仅需要以图文结合的形式展示解题过程，还需提供图文对齐解析数据集及长步骤推理数据集的交互式展示，支持关键步骤高亮和逻辑推导过程查看。

在异常处理方面，系统需具备基本的状态识别与提示能力。针对输入为空、图像缺失或网络异常等情况提供明确提示；对个别求解器执行超时或环境依赖错误进行隔离处理，避免局部模型异常影响整体页面展示和其他模型结果返回。

\xsection{系统设计与实现}{System Design and Implementation}

\xsubsection{系统总体架构}{Overall System Architecture}

为满足多模态几何题在线求解与多模型对比分析的业务需求，系统在整体架构上采用前后端分离的 B/S（Browser/Server）架构，基于自顶向下、逐步求精的结构化设计方法，将界面展示、交互通信、应用服务、模型执行以及数据存储进行分层设计。该设计有助于降低前端页面与后端算法模块之间的耦合度，也便于后端独立部署不同求解算法与运行环境。系统总体架构如图~\ref{fig:system_arch} 所示。

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.95\textwidth]{c5_system_arch.pdf}
    \caption{系统总体架构}

系统整体可划分为前端展示层、交互控制层、后端服务层与数据支撑层四个部分。前端展示层基于 Vue.js 框架构建，负责用户参数输入、页面路由跳转以及可视化结果渲染；交互控制层基于 HTTP 和 JSON 协议规范，通过 RESTful API 完成请求发送、数据校验与返回结果解析；后端服务层基于 Python 的 FastAPI 框架开发，其内部的 Controller 模块负责路由管理、任务分发与结果组织，同时包含生成、衍生、求解与数据集管理等核心业务模块；数据支撑层则承担题目记录、运行日志及缓存管理等功能，依赖 MySQL 等组件为用户多次运行提供存储支持。通过上述分层设计，系统能够较清晰地组织多模态输入、模型调用和结果展示流程，并在异常情况下返回相应状态信息。

\xsubsection{系统核心模块}{Core Module}

围绕平面几何问题求解这一核心任务，系统在功能实现上主要包括输入管理、模型选择与调度、求解执行以及结果展示四个部分。

输入管理模块主要负责接收用户提交的题目文本和几何图像，并完成基础的数据校验与请求封装。模型选择与调度模块是核心控制单元，后端 Controller 依据用户在前端选择的求解模型，匹配对应算法的执行接口与运行环境。

求解执行模块负责调用具体的几何求解算法。系统在此处集成了四种具有不同技术路线的求解方法：第一为树状搜索求解（GeoTree），该模块通过定理检索器与符号求解器协作，底层采用蒙特卡洛树搜索（MCTS）及 UCT 公式以平衡证明路径的探索与利用；第二为演绎可解释求解，作为 Inter-GPS 的增强版本，该引擎将预定义的几何定理集作为产生式规则，通过自顶向下的逻辑演绎生成可读的证明链；第三为大模型求解，系统调用本地部署的大语言模型（如 Qwen-Math 或 DeepSeek），通过思维链（Chain-of-Thought, CoT）提示词技术将复杂问题拆解为自然语言子步骤；第四为神经符号求解，感知层利用神经网络进行图形目标检测与 Bounding Box 标注，逻辑层则将感知谓词输入符号推理机执行求解。

结果展示模块负责对后端返回的 JSON 格式数据进行统一可视化呈现。系统对返回结果进行结构化处理，提取模型名称、执行状态、关键推理过程以及附加的四元组标签（难度、求解步数、求解时间、涉及定理），并按照不同求解模型划分展示区域，使用户能够直观查看各模型的求解过程与输出差异。

\xsubsection{系统实现}{System Implementation}

\subsubsection{几何求解模块实现}

在系统具体实现层面，本章围绕平面几何问题求解流程，对前端交互、后端接口、请求数据封装以及多模型求解模块进行了工程化组织。由于系统后端主要采用模块化函数调用方式实现，而非完全基于面向对象的继承结构进行开发，因此本章采用软件工程中 UML 风格的类图对系统求解模块中的关键文件、数据对象及其调用关系进行抽象描述，如图~\ref{fig:c5_class} 所示。

几何求解模块主要由前端层、求解入口与数据传输对象、求解核心模块三部分组成。前端层基于 Vue.js 实现用户交互，负责接收题目文本、几何图像以及用户选择的求解模型，并通过 Axios 向后端的 main\_solver 接口发送请求。求解入口层以 main\_solver.py 作为统一控制入口，通过 FastAPI 的路由机制接收前端请求，并将请求体封装为 TextAndImageRequest 数据对象。该对象包含 problem\_str、image\_base64 和 model 三个核心字段，分别用于表示题目文本、图像编码以及用户指定的求解模型类型。求解核心模块由 GeoTree、InterGPS、大语言模型和神经网络四类求解模块组成，各模块在输入形式上保持一致，均以题目文本和图像编码作为主要输入，并在执行完成后返回求解文本、求解时间、难度标签和涉及定理等结构化结果。

@router.post("/main_solver")
async def main_solver(request: TextAndImageRequest):
    logger.info(f"Received problem_str: {request.problem_str}")

    if not request.problem_str:
        raise HTTPException(status_code=400, detail="请提供完整的题目文本")

    if request.model == "model1":
        answer = model1_solve.geotree_solve(request.problem_str, request.image_base64)
    elif request.model == "model2":
        answer = model2_solve.intergps_solve(request.problem_str, request.image_base64)
    elif request.model == "model3":
        answer = model3_solve.llm_solve(request.problem_str, request.image_base64)
    elif request.model == "model4":
        answer = model4_solve.nn_solve(request.problem_str, request.image_base64)
    else:
        raise HTTPException(status_code=400, detail="不支持的模型类型")

    return JSONResponse(content=answer)

\subsubsection{前后端通信}

系统前后端之间采用基于 HTTP/JSON 协议的数据交换方式。前端通过 Axios 向后端 FastAPI 接口发送请求，请求中包含题目文本、图像编码及模型配置信息。后端接收到请求后，完成合法性校验，并将任务转交 Controller 分发给对应的求解器执行。

考虑到不同模型在推理耗时上的差异，前端页面按照模型维度组织结果展示区域。后端返回结构化结果后，前端根据返回数据更新对应模型的展示区域，而无需重新渲染整个页面。若某一模型在执行过程中超时或抛出异常，系统会将异常状态封装为标准响应，由前端独立渲染失败状态，从而避免单个模型异常影响其他模型结果的展示。

\subsubsection{后端服务与模型部署}

系统后端服务主要依托 FastAPI 构建，通过路由函数对外提供几何求解接口，并在接口内部完成请求解析、模型选择和结果返回。

在模型部署层面，由于四类求解器对底层依赖库（如 PyTorch、SymPy）和 Python 运行环境的要求存在差异，系统采用基于虚拟环境的隔离式部署策略。具体而言，系统为异构算法配置独立的 Conda 环境或子进程，后端 Controller 通过标准化的脚本调用接口完成环境唤起、参数传递与结果回收。该设计减少了不同模型依赖冲突对系统运行的影响，也为后续接入新的几何求解算法提供了较清晰的扩展方式。

在异常处理方面，后端服务层在执行边界统一捕获外部依赖调用失败、脚本运行异常等情况，并将异常信息格式化为 JSON 响应返回前端，从而隔离局部模型异常对整体业务流程的影响。

\subsubsection{数据存储与缓存}

在数据存储层，系统采用 MySQL 关系型数据库保存长期结构化信息。其核心存储内容包括用户提交的文本记录、图像文件映射路径、题目求解元数据以及供数据集展示模块调用的索引关联信息。

为减少重复题目带来的冗余计算，系统引入 Redis 内存数据库作为缓存支撑。当用户重复提交相同题干与配图时，后端优先计算输入特征的哈希键并向 Redis 缓存发起检索，若命中缓存数据则直接复用历史 JSON 结果，减少对底层求解引擎的重复调用。同时，在多模型求解场景中，Redis 可用于暂存任务执行状态和中间结果，辅助前后端进行状态同步与结果更新。

通过上述实现，系统将前端输入、后端接口、模型调用和结果返回连接成一个完整流程。用户提交题目后，后端根据模型参数调用对应的求解模块，并将结果统一返回给前端展示；同时，通过独立部署环境和缓存机制，减少不同模型之间的依赖冲突问题。

当用户点击“开始求解”后，系统在右侧结果区逐步呈现各模型的求解输出，如图~\ref{fig:solver_page_result} 所示。结果区以模型为单位组织内容，不同模型的展示形式与其求解特点相对应。树状搜索求解结果更强调形式化解析与结构化推理，例如点、线、圆及其关系的形式表示，并结合图像中的关键元素高亮或局部识别结果，以体现其对图形结构的搜索能力；演绎可解释求解结果则以文字证明链为主，按照步骤给出条件、定理调用与推导过程，突出推理过程的可读性；大模型求解结果主要采用自然语言组织答案与分析，更接近日常题解的表述方式；神经符号求解结果则偏向解析几何式的计算过程，体现符号约束与数值推导相结合的求解路径。

由图~\ref{fig:solver_page_result} 可以看出，结果区采用纵向卡片的方式组织多模型输出。当前已展开的树状搜索求解结果面板中，页面展示了题目的求解步骤、图形解析结果以及附加属性信息；其下方的演绎可解释求解结果继续以独立面板形式呈现，并在标题区域标识当前状态。这样的设计既保证了不同模型结果的独立性，也便于用户在同一页面内进行直接比较，从而更清楚地观察不同方法在同一道几何题上的表现差异。

此外，为了增强结果的可比较性，系统在各模型结果末尾统一附加四元组标签信息，即难度、求解步数、求解时间和涉及定理。该部分内容能够在较高层面对当前结果作出概括，一方面反映题目与推理过程的复杂程度，另一方面也提供了运行效率和知识调用方面的补充信息，从而为模型分析和案例比较提供辅助依据。总体而言，页面展示模块实现了从首页入口到结果呈现的完整交互过程，能够较好支撑平面几何问题的多模型求解与结果对比。
