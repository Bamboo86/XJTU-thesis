\xchapter{平面几何问题求解系统}{Plane geometry problem solving system}

% 前文构建了面向长步骤平面几何推理的多模态数据基准，为复杂几何任务提供了统一的评测基础；同时还提出了面向长链条平面几何推理的两阶段增强方法，为几何问题自动求解提供了有效的技术支撑。
为了进一步验证前述研究成果在实际应用场景中的可行性，并推动相关方法由离线实验走向系统落地，本文在前述工作的基础上开发了平面几何问题求解系统，对多模态输入、求解模型、数据集展示与结果可视化流程进行了统一集成。本章围绕系统的需求分析、系统设计与实现、系统展示与测试等内容展开说明，重点介绍几何求解模块的工程化实现过程。

\xsection{系统需求分析}{System Requirement Analysis}

\xsubsection{功能性需求分析}{Functional Requirement Analysis}

平面几何问题求解系统主要定位为面向教育领域及个性化教学的辅助平台，适用对象涵盖进行几何学习的学生、准备教学资源的教师以及相关领域的算法研究人员。与仅输出最终答案的传统数学工具相比，本系统旨在实现用户需求与后端智能算法的无缝对接。在功能设计上，系统主要包含以下几项核心需求：

在题目生成与输入方面，系统应具备智能化大规模生成几何问题及问题拓展衍生的功能，能够根据设定的难度、几何基元及定理参数进行自动化生成。针对用户自定义求解，系统需支持输入平面几何题目的文字描述并上传几何图像，以贴近“题干+配图”的多模态组织形式。

在多模态求解与模型调用方面，系统应在统一框架下集成四种主流求解算法：树状搜索、演绎可解释、大模型以及神经符号求解。前端需提供直观的模型勾选与切换功能，后端则负责不同模型运行环境的独立管理与统一调度，实现同一题目在不同求解方法下的横向对比。

在求解流程与可视化展示方面，系统应采用异步并行调度机制。提交任务后，不必等待全部模型完成即可优先返回已完成的结果。系统不仅需要以图文并茂的形式展示解题过程，还需提供高质量图文对齐解析数据集及长步骤推理数据集的交互式展示，支持高亮演示及逻辑推导的可视化。

在异常处理方面，系统需具备完善的状态识别能力。针对输入为空、图像缺失或网络异常等情况提供明确提示；对个别求解器执行超时或环境依赖错误进行有效隔离，保证系统在多模型并发场景下的连续性与整体可用性。

\xsubsection{非功能性需求分析}{Non-Functional Requirement Analysis}

除功能性需求之外，平面几何问题求解系统还需满足实际部署与运行环境下的非功能性要求，以保证系统在多并发和复杂推理下的可用性、响应效率与稳定性。

在运行与开发环境约束方面，系统基于前后端分离的 B/S 架构开发。客户端需支持运行 Chrome 或 Edge 等现代浏览器的操作系统（如 Windows、Linux、MacOS 等）。在服务端，普通运行环境需满足 CPU i5、8G 内存、256G 硬盘及 4G 显存的底线配置；由于系统集成了多种深度学习与大语言模型，开发与高负载运行环境需配备 i7 及以上 CPU、16G 内存以及至少 8G 显存，且高度依赖网络环境的稳定性。

在系统性能与响应效率方面，系统前端基于 Vue.js 框架构建，后端基于 FastAPI 封装算法接口。借助 FastAPI 的异步特性，系统应在并发调用多个求解模型时尽量减少用户的感知等待时间，保证结果展示具有良好的实时性和连贯性。

在可扩展性与可维护性方面，系统总体源程序量约为 6200 行，其架构设计必须保持高度模块化与低耦合。前端交互模块（负责路由与渲染）与后端支撑模块（Generation、Derivation、Solver、Manager）需职责清晰。这种设计不仅确保系统能够以较低成本快速接入未来新增的几何求解算法，也有助于长期的维护与系统升级。

\xsection{系统设计与实现}{System Design and Implementation}

\xsubsection{系统总体架构}{Overall System Architecture}

为满足多模态几何题在线求解与多模型对比分析的业务需求，系统在整体架构上采用前后端分离的 B/S（Browser/Server）架构，基于自顶向下、逐步求精的结构化设计方法，将界面展示、交互通信、应用服务、模型执行以及数据存储进行深度解耦。该设计不仅有助于提升页面响应效率，也便于后端独立部署不同求解算法与运行环境，从而更好地支持大规模的用户访问与高并发处理。系统总体架构图如~\ref{fig:system_arch} 所示。

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.95\textwidth]{c5_system_arch.pdf}

系统整体可划分为前端展示层、交互控制层、后端服务层与数据支撑层四个部分。前端展示层基于 Vue.js 框架构建，负责用户参数输入、页面路由跳转以及可视化结果渲染；交互控制层基于 HTTP 和 JSON 协议规范，通过 RESTful API 完成异步请求发送、数据校验与返回结果解析；后端服务层基于 Python 的 FastAPI 框架开发，其内部的 Controller 模块负责路由管理、任务分发与结果聚合，同时包含底层核心业务模块（生成、衍生、求解与数据集管理）；数据支撑层则承担题目记录、运行日志及热点缓存管理等功能，依赖 MySQL 等组件为用户多次运行提供存储支持。同时，系统具有高效的错误处理和异常管理能力，保证系统稳定运行。

\xsubsection{系统核心模块}{Core Module}

围绕平面几何问题求解这一核心任务，系统在功能实现上主要包括输入管理、模型选择与调度、求解执行、以及结果展示四个部分。

输入管理模块主要负责接收用户提交的题目文本、几何图像，并完成基础的数据校验与请求封装。模型选择与调度模块是核心控制单元，后端 Controller 依据用户前端选择的求解模型，动态匹配对应算法的执行接口与运行环境。

求解执行模块负责调用具体的几何求解算法。系统在此处集成了四种具备不同工程特点的求解路线：其一为树状搜索求解（GeoTree），该模块通过定理检索器与符号求解器协作，底层采用蒙特卡洛树搜索（MCTS）及 UCT 公式以平衡证明路径的探索与利用；其二为演绎可解释求解，作为 Inter-GPS 的增强版本，该引擎将预定义的几何定理集作为产生式规则，通过自顶向下的逻辑演绎生成严密可读的证明链；其三为大模型求解，系统调用本地部署的大语言模型（如 Qwen-Math 或 DeepSeek），通过思维链（Chain-of-Thought, CoT）提示词技术将复杂问题拆解为自然语言子步骤；其四为神经符号求解，感知层利用神经网络进行图形目标检测与 Bounding Box 标注，逻辑层则将感知谓词输入符号推理机执行严谨求解。

结果展示模块负责对后端返回的 JSON 格式数据进行统一可视化呈现。系统对返回结果进行结构化处理，提取模型名称、执行状态、关键推理过程以及附加的四元组标签（难度、求解步数、求解时间、涉及定理），从而支持多模型的独立呈现与横向比较。

\subsubsection{前后端通信}

系统前后端之间采用基于 HTTP/JSON 协议的异步方式进行数据交换。前端通过 Axios 向后端 FastAPI 接口发送请求，请求中包含多模态数据及模型配置信息。后端接收到请求后，完成合法性校验，随即将任务转交 Controller 分发给对应的求解器执行。

考虑到异构模型在推理耗时上的差异，前后端通信设计为分阶段响应机制。后端在各模型执行过程中持续维护任务状态机，并将已经完成的结构化结果优先通过异步回调发送给前端。前端在接收到局部结果后，结合 Update View 机制仅刷新对应模型的展示区域，而无需阻塞等待全部任务完成。若某一模型在执行过程中超时或抛出异常，前端会独立渲染失败状态，保证了整个系统在多并发任务下的容错率与交互稳定性。

\subsubsection{后端服务与模型部署}

系统后端服务主要依托 FastAPI 构建，其原生的异步 IO 特性在承载多模型并行调用和高频接口请求方面具有显著的架构优势。

在模型部署层面，由于四类求解器对底层依赖库（如 PyTorch、SymPy）和 Python 运行环境的要求存在冲突，系统采用基于虚拟环境的隔离式部署策略。具体而言，系统为异构算法配置独立的 Conda 环境或子进程，后端 Controller 充当调度员，通过标准化的脚本调用接口完成环境唤起、参数传递与结果回收。这一设计也为未来新增科研算法提供了标准化插件接入能力，实现了算法的热插拔。

在异常处理方面，后端服务层在执行边界统一捕获外部依赖调用失败、脚本运行异常等不确定因素，并将异常信息格式化为标准 JSON 响应前端，有效隔离了局部模型崩溃对全局业务链路的影响。

\subsubsection{数据存储与缓存}

在数据存储层，系统采用 MySQL 关系型数据库保存长期结构化信息。其核心存储包括用户提交的文本记录、图像文件映射路径、题目求解元数据以及供数据集展示模块调用的索引关联信息。

为缓解深度学习模型和复杂符号计算带来的算力压力，系统引入 Redis 内存数据库作为高频缓存支撑。当用户重复提交相同题干与配图时，后端优先计算输入特征的哈希键并向 Redis 缓存发起检索，若命中热点数据则直接重用历史 JSON 结果，从而大幅削减底层计算引擎的冗余拉起开销。同时，在多模型长时异步求解场景中，Redis 亦用于暂存分布式任务的中间状态，保障了前后端状态同步的平滑度与整体处理效率。

\xsection{系统展示与测试}{System Display and Testing}

\subsubsection{页面展示}

为了便于用户在统一平台中完成几何任务的使用与切换，系统在界面层面采用了“左侧导航栏 + 右侧功能区”的整体布局。首页作为整个几何项目的统一入口，主要用于展示系统标识及各功能模块之间的关系，如图~\ref{fig:system_homepage} 所示。页面左侧为纵向导航栏，顶部展示“GeoSeek 几何求索”的名称与图标，下方依次设置“首页”“几何生成”“几何求解”和“数据集展示”等标签页，用户可通过导航栏在不同页面之间切换。右侧为首页主体区域，上方居中展示 GeoSeek 标识及几何主题图形，下方则以模块入口的形式给出“几何生成”“几何求解”和“数据集展示”三个功能板块。整体来看，首页布局较为简洁，功能划分也较为明确，能够直观呈现系统的基本结构。

首页的作用不仅提供页面跳转入口，也能从整体上组织系统内部的功能关系。其中，“几何生成”模块主要用于几何题目及图像样例的构造，可支持随机生成，也可依据预设范式生成相应样例，其在系统中承担了样例构造与任务准备的辅助作用。“几何求解”模块对应本章核心开发模块，是平面几何问题求解方法的主要承载页面。“数据集展示”模块则主要用于数据资源的浏览与查看，在系统中起到展示分析的作用。通过首页的统一组织，系统各模块之间形成了较清晰的层次关系，也使几何求解功能能够被放置在完整项目框架下加以理解。

在此基础上，平面几何问题求解页面采用“左侧输入区 + 右侧结果区”的双栏布局，在统一界面风格下完成题目输入、模型配置以及结果展示。页面左侧保留系统导航栏，主体区域顶部显示“几何问题求解器”标题，页面的主要交互过程围绕“输入--求解--展示”这一流程展开。

当用户点击“开始求解”后，系统在右侧结果区逐步呈现各模型的求解输出，如图~\ref{fig:solver_page_result} 所示。结果区以模型为单位组织内容，不同模型的展示形式与其求解特点相对应。树状搜索求解结果更强调形式化解析与结构化推理，例如点、线、圆及其关系的形式表示，并结合图像中的关键元素高亮或局部识别结果，以体现其对图形结构的搜索能力；演绎可解释求解结果则以文字证明链为主，按照步骤给出条件、定理调用与推导过程，突出推理过程的可读性；大模型求解结果主要采用自然语言组织答案与分析，更接近日常题解的表述方式；神经符号求解结果则偏向解析几何式的计算过程，体现符号约束与数值推导相结合的求解路径。

由图~\ref{fig:solver_page_result}可以看出，结果区采用纵向卡片的方式组织多模型输出。当前已展开的树状搜索求解结果面板中，页面展示了题目的求解步骤、图形解析结果以及附加属性信息；其下方的演绎可解释求解结果继续以独立面板形式呈现，并在标题区域标识当前状态。这样的设计既保证了不同模型结果的独立性，也便于用户在同一页面内进行直接比较，从而更清楚地观察不同方法在同一道几何题上的表现差异。

此外，为了增强结果的可比较性，系统在各模型结果末尾统一附加四元组标签信息，即难度、求解步数、求解时间和涉及定理。该部分内容能够在较高层面对当前结果作出概括，一方面反映题目与推理过程的复杂程度，另一方面也提供了运行效率和知识调用方面的补充信息，从而为模型分析和案例比较提供辅助依据。总体而言，页面展示模块实现了从首页入口到结果呈现的完整交互过程，能够较好支撑平面几何问题的多模型求解与结果对比。
